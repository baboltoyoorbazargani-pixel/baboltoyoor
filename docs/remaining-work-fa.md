# تکمیل مرحلهٔ دوم پایدارسازی

این مرحله روی شاخهٔ کاری انجام شده و نسخهٔ عمومی 1.0.87 را بازنویسی نمی‌کند. هیچ تنظیم عملیاتی، دیتابیس مشتری، دامنه، حساب ویندوز یا سرویس خارجی در این محیط تغییر نکرده است.

## ۱. اصلاح خطای نصب‌کننده در checkout ویندوز

تست‌های نصب‌کننده محتویات اسکریپت PowerShell را با Payload داخل CMD بایت‌به‌بایت مقایسه می‌کنند؛ تبدیل LF به CRLF هنگام checkout ویندوز این قرارداد را می‌شکست. فایل `.gitattributes` اکنون سورس متنی را LF و فایل CMD تولیدشده را با بایت‌های CRLF اصلی حفظ می‌کند. خود تست‌ها شل نشده‌اند. `tests/windows-checkout.test.js` با index موقت و `core.autocrlf=true` همین وضعیت را آزمایش می‌کند، بدون دست‌زدن به index کاربر. اجرای واقعی PowerShell در job ویندوز CI همچنان ضروری است.

## ۲. انتخاب حساب کم‌اختیار برای سرویس

گزینهٔ جدید نصب‌کننده:

```powershell
BabolToyor-Setup.cmd install -ServiceAccount "LOCAL SERVICE"
```

حساب با SID شناخته‌شدهٔ S-1-5-19 و RunLevel محدود اجرا می‌شود؛ به پوشهٔ برنامه فقط ReadAndExecute، به data و logs مجوز Modify و به `.env` فقط Read اضافه می‌شود. پوشهٔ supervisor قابل‌نوشتن توسط این حساب نیست. خطای ACL نصب را متوقف می‌کند. این گزینه برای نصب جدید یا ارتقای صریح است؛ پیش‌فرض SYSTEM برای جلوگیری از قطع ناگهانی نصب‌های موجود حفظ شده است.

محدودیت‌ها: این کار مجوزهای اضافی موروثیِ یک سرور بدپیکربندی‌شده را حذف نمی‌کند؛ ACL پوشهٔ نصب را نیز بررسی کنید. Node باید به‌صورت سراسری یا در مسیر برنامه قابل‌خواندن باشد. LOCAL SERVICE برای اشتراک شبکه به‌صورت ناشناس وصل می‌شود؛ برای بکاپ UNC ممکن است حساب دامنهٔ اختصاصی لازم باشد. ایجاد قاعدهٔ فایروال HTTPS را مدیر سرور انجام دهد؛ حساب کم‌اختیار نباید برای این منظور ارتقا یابد. پیش از تغییر حساب، شروع مجدد، تمدید گواهی و نوشتن بکاپ را روی ویندوز آزمایش کنید.

## ۳. مهاجرت اختیاری قیود دیتابیس

هیچ مهاجرت جدیدی خودکار هنگام Startup اجرا نمی‌شود. مسیر صریح:

```sh
node scripts/migrate-integrity.js /absolute/path/baboltoyoor.db
# سرویس را متوقف کنید؛ DATA_DIR باید به پوشهٔ واقعی قفل سرویس اشاره کند.
node scripts/migrate-integrity.js /absolute/path/baboltoyoor.db --apply --confirm-offline
```

ابتدا فقط گزارش پیش‌بررسی تولید می‌شود. برای اعمال، دیتابیس باید سالم و بدون ناسازگاری گزارش‌شده باشد و فایل قفل برنامه نباید وجود داشته باشد. قفل قدیمی را تنها پس از اطمینان از توقف سرویس بررسی کنید؛ ابزار خودسرانه آن را حذف نمی‌کند.

قبل از تغییر، Snapshot خصوصی با پسوند `.before-integrity-….db` کنار دیتابیس ساخته می‌شود. در یک تراکنش، یکتایی نام کاربری بدون حساسیت به حروف و روابط زیر اضافه می‌شوند:

- order_items.order_id → orders.id
- order_items.product_id → products.id
- payments.order_id → orders.id

روابط از نوع DEFERRABLE INITIALLY DEFERRED هستند تا ذخیره و بازیابی چندجدولی در پایان تراکنش اعتبارسنجی شوند. ستون‌ها، Payload، ایندکس‌های قبلی و ترتیب رکوردها حفظ می‌شوند؛ رکوردی حذف یا شماره‌گذاری مجدد نمی‌شود. اجرای مجدد مجاز است. تست‌ها رد رکورد یتیم، نام کاربری تکراری و Restore از Snapshot قبل از مهاجرت را بررسی می‌کنند.

عمداً یکتایی شمارهٔ سفارش/فاکتور و رابطهٔ همهٔ موجودیت‌های قدیمی تحمیل نشده است؛ قواعد شعب و استثناهای Legacy نیازمند تصمیم تجاری هستند. این مهاجرت در محیط عملیاتی اجرا نشده است. بازگشت schema فقط به‌صورت آفلاین با Snapshot قبل از مهاجرت و ارزیابی عملیات جدید انجام شود؛ Restore داده از داخل برنامه قیود نصب‌شده را حذف نمی‌کند.

## ۴. پشتیبان رمزگذاری‌شده و انتقال به مقصد مستقل

```sh
# BT_BACKUP_PASSPHRASE را از secret store به محیط فرایند تزریق کنید؛ در CLI ننویسید.
node scripts/encrypted-backup.js encrypt /source/baboltoyoor.db /independent-volume/export.bte
node scripts/encrypted-backup.js decrypt /independent-volume/export.bte /private-folder/restored.db
```

رمز باید ۱۶ تا ۱۰۲۴ نویسه داشته باشد. ابزار با اتصال فقط‌خواندنی، Snapshot یکپارچه می‌سازد؛ سپس با scrypt و AES-256-GCM رمزگذاری می‌کند. Header نیز احراز اصالت می‌شود. خروجی تا پایان موفقیت به نام نهایی منتشر نمی‌شود و فایل موجود بازنویسی نمی‌شود. رمز غلط یا دستکاری فایل باعث شکست و حذف خروجی موقت می‌شود. فایل رمزگشایی‌شده خودکار جایگزین دیتابیس برنامه نمی‌شود؛ برای بازیابی از مسیر بررسی‌شدهٔ مدیر استفاده کنید.

مقصد باید از hard link پشتیبانی کند. انتخاب مقصد مستقل، مجوزهای محدود، زمان‌بندی و نگهداری امن رمز بر عهدهٔ استقرار است؛ این ابزار خودش به فضای ابری وصل نمی‌شود و بکاپ خودکار ساعتی موجود را بی‌اجازه به قالب جدید تبدیل نمی‌کند. روی ویندوز ACL پوشهٔ موقت و مقصد رمزگشایی را محدود کنید. رمز را جدا از بکاپ نگه دارید؛ گم‌شدن آن غیرقابل‌بازیابی است.

## ۵. هشدار بیرونی

برای همان ابزار `scripts/check-service.js`، تنظیمات اختیاری زیر را در محیط مانیتور مستقل تعریف کنید:

```dotenv
BT_ALERT_WEBHOOK_URL=https://YOUR-MONITORING-ENDPOINT/alerts
BT_ALERT_WEBHOOK_TOKEN=YOUR_SECRET_TOKEN
```

توکن اختیاری است؛ در URL نام کاربری/رمز نگذارید. هنگام شکست بررسی سرویس یا بکاپ، یک POST کوچک بدون اطلاعات مشتری، محتویات بکاپ یا متن خطای داخلی ارسال می‌شود. مقصد باید HTTPS باشد؛ Redirect دنبال نمی‌شود، Timeout محدود است و خطای ارسال، exit code شکست را حفظ می‌کند. ابزار باید مستقل از برنامه با Task Scheduler/cron اجرا شود تا توقف برنامه نیز قابل تشخیص باشد. اتصال واقعی به سرویس هشدار در این محیط انجام نشده است؛ محدودسازی تکرار و escalation را سامانهٔ مانیتورینگ مدیریت کند.

## ۶. صفحه‌بندی SQL و سنجش سرعت

فهرست `/api/orders` و تاریخچهٔ `/api/sales/history` اکنون فیلتر، شمارش، جست‌وجو و LIMIT/OFFSET را در SQL اجرا می‌کنند و فقط صفحهٔ منتخب را برمی‌گردانند. کنترل نقش نگهبان/انبار، جست‌وجوی literal (نه wildcard)، حروف Unicode و جست‌وجوی شمارهٔ فاکتور آزموده شده‌اند. این تغییر، کل معماری حافظه‌ای برنامه را حذف نمی‌کند؛ بخش‌های گزارش و شاخص‌های جانبی هنوز می‌توانند داده‌ها را در حافظه پیمایش کنند.

```sh
node scripts/benchmark-order-search.js 10000
```

Benchmark همیشه دیتابیس مصنوعی موقت می‌سازد و DATA_DIR/SQLITE_FILE عملیاتی را استفاده نمی‌کند. در اجرای محلی با ۱۰هزار سفارش و ۳۰ تکرار، صدک ۹۵ تقریباً ۱٫۵ms برای صفحهٔ فروش، ۷٫۹ms برای انبار، ۳۹٫۲ms برای جست‌وجو و ۱۲ms برای تاریخچه بود. این اعداد تست بار هم‌زمان، شبکه یا تعهد کارایی روی سرور مشتری نیستند.

## مواردی که همچنان نیازمند محیط واقعی یا مرحلهٔ معماری بعدی‌اند

- دامنه، DNS، صدور/تمدید گواهی و فایروال عملیاتی؛ بدون این اطلاعات نمی‌توان HTTPS واقعی را تکمیل کرد.
- پذیرش نصب و حساب سرویس روی Windows Server، اشتراک شبکه، چاپگر و باسکول واقعی.
- اجرای مهاجرت روی کپی دادهٔ واقعی، تأیید قواعد شماره‌گذاری و سپس پنجرهٔ نگهداری عملیاتی.
- زمان‌بندی انتقال بکاپ رمزگذاری‌شده، اتصال Webhook واقعی و تمرین بازیابی با RPO/RTO توافق‌شده.
- تفکیک کامل app.js/ui2.js، حذف سراسری Proxy و انتقال همهٔ گزارش‌ها به SQL. این بازنویسی بزرگ با اصلاح نصب و قیود مالی یک‌جا انجام نشده است.
- تست بار هم‌زمان و پذیرش دسترس‌پذیری با کاربران واقعی.
